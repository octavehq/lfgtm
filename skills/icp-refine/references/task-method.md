# icp-refine: task method

Load [gtm-context.md](../../shared/gtm-context.md) and identify the refinement scope: offering,
Motion, persona × segment cells, playbooks, current qualification criteria,
triggers, and disqualifiers. Read full selected entities/cells. Segment is
one dimension of ICP; the same company type can fit renewal and net-new
differently. Services and Solutions are first-class offerings.

Load [analytics-contract.md](../../shared/analytics-contract.md). Build one opportunity row per final
outcome with firmographics, use case, buying roles, motion, acquisition
source, pursued/qualified status where recorded, win/loss, value, cycle,
and supporting conversations. Compare like cohorts. Report pursuit exposure
and closed win rate together; “common among wins” is descriptive, not proof
of highest propensity. Do not divide wins by an unrelated population.

For each candidate segment show: eligible/pursued/closed counts as available;
won/lost and win rate; value/cycle; observed reasons; source coverage and
uncertainty; and untested alternatives. Ask for supplementary retention,
expansion, delivery-cost, or POC/value data only when material to the user's
objective. Incorporate sourced operator answers. If unavailable, state the
remaining uncertainty and propose a bounded segment test or future measure.
Do not invent lifetime value or treat absent history as poor fit.

Classify each proposed signal before proposing an ICP change:
- Structural fit: stable capability, use-case, scale, geography, or delivery
  compatibility; evidence may support inclusion or exclusion.
- Readiness/trigger: priority, budget timing, change event, active evaluation.
- Execution: missing champion, weak discovery, single-threading, poor proof.
- Commercial constraint: economically viable deal/terms or delivery model.
- Competitive/product gap: specific unmet requirement or stronger alternative.
- Unknown: not observed, conflicting, or not inferable from current sources.

A loss association alone cannot create a disqualifier. For each proposed
criterion specify target entity/cell; question/definition; rationale;
observable evidence; public-research versus discovery-only availability;
answer labels; unknown behavior; score/weight or true disqualifier role;
exceptions; source support; and likely false positives/negatives.

Use a true disqualifier only for an evidenced incompatibility that prevents
a viable sale/delivery in this offering/Motion. No public budget, no visible
champion, or a junior evaluator must remain unknown/readiness/execution,
not automatic account rejection. Identify the coaching or nurture action
for remediable conditions instead of narrowing ICP to hide execution gaps.

Propose a before/after criterion set and a small holdout: known-fit wins,
known-fit losses, genuine nonfit accounts, underrepresented segments, and
unknown-evidence cases. Define expected distinctions before inspecting
revised results. Use the existing qualification-validation workflow and
current configured agents/tools when available; do not invent a scoring
endpoint. Test answer-level sourcing, unknown handling, true-disqualifier
semantics, false rejections, and changed rankings.

If runtime testing is unavailable, deliver the exact proposed criteria,
fixtures, expected results, and pending validation step; do not call the
stored changes runtime-validated. Keep the workflow open for supplied
examples/results. When application is requested, load
[workspace-mutations.md](../../shared/workspace-mutations.md); apply exact validated entity/cell changes,
preserve prior rationale/source, and read back. Load [output-readiness.md](../../shared/output-readiness.md) at
delivery and distinguish proposal, stored update, and behavior validation.
